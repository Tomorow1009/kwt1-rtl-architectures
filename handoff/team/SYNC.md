# 队友修改后的再次同步

Git已合并提交是团队基准；服务器独立快照是验证证据。不要靠修改时间或文件夹名称判断最新版。

## 正常往返

1. `git status --short` 检查未提交内容。先保存个人工作，再fetch；没有本地改动时可 `git pull --ff-only`。不自动reset/clean，不覆盖改动。
2. `git switch -c codex/<成员>/<任务>`，修改workspaces/arch02或团队工具文档。历史版本目录不动。
3. 运行与改动相关的检查。文档变更检查链接与命令；RTL/SRAM适配变更需定向及必要完整回归。记录未运行项目。
4. 提交受测源码；打包时记录source_commit和哈希。上传新目录，不覆盖r03或队友快照。
5. 服务器按阶段运行；原始结果留服务器。Git提交摘要、运行路径、受测提交、数据及配置哈希，不能复制PASS到未验证提交。
6. 推送个人分支，创建PR并合并。合并冲突如果改变代码，要重新验证受影响内容。结果提交可晚于受测提交，但必须明确两者关系。
7. 下一位成员拉取合并结果，检查STATUS及运行状态，再开始下一轮。

## 服务器临时修改

优先改本地Git后上传。确需现场诊断时，在新的个人副本改，记录修改前哈希和具体差异；运行中的快照不能改。将修改准确落实到本地Git、重新打包验证，才可交接。无法通过允许的摘要/截图恢复时标记“未同步临时改动”，不得宣布同步完成。

当前服务器到本地不默认回传文件。不要自行启用新通道；厂商库和凭据不回传。代码用Git同步，服务器输入用新包同步，大型结果用运行索引同步。

## 冲突、运行锁与中断

共享VNC同一时刻只允许一人操作。server.py对合作工具使用服务器根目录 `.arch02_team_lock`，它无法约束绕开入口的手工命令，因此还要观察桌面和进程。

`server.py status --session <名字>`显示已有阶段、驱动PID和子进程存活情况。PID存活仍需核对主机/命令，防止PID复用。不得因屏幕刷新超时而重启作业。锁残留时不自动删除：核实所有相关进程确已终止，再由负责人处理。

通过阶段不能原地重跑；失败阶段也保留。需要重试时建立新session，完整all入口不会跳过旧阶段。分阶段继续只允许前一阶段通过且当前阶段从未记录；这样避免悄悄复用失败产物。

## 每轮更新内容

STATUS记录：受测提交、结果提交或PR、成员、源码/数据/配置哈希、运行目录、已通过/失败/未运行项目、运行中任务、临时改动、下一步和更新时间。个人工具路径不放共享STATUS。

未来版本从通过验证的开发提交建立新快照，旧版保留；不自动给每次实验创建发布版本。
